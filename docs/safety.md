# Verification and cleanup safety

Exact duplicate means equal logical length and all equal bytes in the primary stream of distinct physical files. It says nothing about semantic similarity or safe interchangeability. Hard-link paths collapse to one volume/file identity. Their link count is retained and cleanup is disabled. Empty files are opt-in and represent zero logical savings.

Reads open with FILE_SHARE_READ only. Ordinary Windows writers, replacement, rename and deletion are denied while handles are held. Metadata and volume/file identities are captured from handles, then checked after reading and again against scan snapshots before cleanup. Read/permission/identity failures invalidate a candidate. There are no retries; repeatedly changing files require a new scan. Length, timestamps, attributes and identity are not a snapshot of an entire live tree. Previously open writable memory mappings, filesystem drivers, network semantics, identity reuse, hardware faults and malicious privileged processes remain outside these guarantees. Verification means compared successfully at scan time, not permanently equal.

Each cleanup reopens both keeper and source, rejects stale snapshots, compares full bytes again, requires equal owner/group/DACL security fingerprints and file attributes, and holds the keeper throughout. Extra streams, unknown stream-enumeration capability, multiple hard links, reparse points, encrypted/sparse/compressed/read-only/system files require manual review and cannot be automatically removed. Windows, Program Files, ProgramData, roaming application data, local Packages/Programs and this application's data paths plus user-protected paths are excluded from cleanup. New protected folders added after scanning are also enforced at planning and execution. Source and keeper cannot be the same physical file; no keeper may also occur among planned sources. Source removal and same-volume rename use the validated handle rather than reopening the path.

Quarantine destinations contain an operation UUID and a random filename. Existing files are never overwritten. Same-volume rename preserves streams and security and does not release allocation. Cross-volume moves create a `.partial` file exclusively, flush it to disk, compare every byte against the locked source, promote it without overwrite, and only then remove the source through its handle. A durable journal records the content hash and original/destination paths. Cancellation or failure can leave both copies or a `.partial` file. Do not delete either until you inspect their contents and journal state. Cross-volume copies preserve primary contents; inherited destination ACLs, creation/access timestamps and all application metadata are not guaranteed to survive. Files with extra streams are refused before automated cleanup.

Restore checks the original path is vacant, rejects reparse ancestors and changed quarantine content using the recorded SHA-256 while holding its handle, then performs a no-overwrite rename or verified copy. Restore conflicts require explicit manual resolution. An interrupted or failed entry cannot be automatically restored, because its filesystem outcome may be ambiguous. Journal and file mutation cannot be committed atomically together; a crash after rename but before journal completion is deliberately shown as interrupted.

Parent directory reparse checks and destination creation are still path-based; a hostile process able to swap ancestors can race these checks. Run against trusted user-owned folder trees, never adversarial namespaces. Mounted volume identity support and file-sharing guarantees vary on remote/filesystem providers. Reparse traversal is disabled even when cloud hydration consent is checked. Native file IDs are the traditional volume serial + 64-bit file index, not the full ReFS 128-bit identity format.

Recycle Bin execution is unavailable: Windows shell recycling is path-based and this version refuses that residual replacement race rather than claiming a handle-bound guarantee. Selecting Recycle records a failed operation explaining that quarantine must be chosen explicitly. There is no permanent-delete fallback. Permanent deletion is irreversible and only works with the advanced checkbox enabled and final confirmation; it uses handle disposition. The batch is sequential and may partially succeed.

Logical redundant bytes are not promised reclaimed storage. Compression, sparse allocation, hard links, allocation units, quarantine volume and Recycle Bin retention affect actual allocation. This version does not calculate physical allocated bytes. Historical results always require rescanning before a new cleanup plan. Every plan is revalidated at execution regardless of age or scan cache.
